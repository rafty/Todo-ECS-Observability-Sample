# Spec: 017-test-data-cleanup

## 概要
- 負荷テストで作成される大量 Todo データを、運用者が手動で一括削除できる仕組みを追加する。
- 削除処理は管理画面/API ではなく、AWS Lambda バッチとして実装する。
- 本サンプルの運用方針に合わせ、`prod` 環境でも同一方式で実行可能とする。

## 背景
- DLT on AWS を用いた負荷テストで、100 名程度のダミーユーザーが同時に API を実行する想定がある。
- テスト後に不要な Todo が大量に残るため、対象データを短時間で削除する手段が必要である。
- 管理者ログイン UI を追加せず、インフラ運用だけで完結する方式が求められている。

## 目的
- 負荷テスト後のデータクリーンアップを、再現可能な手順で実行できるようにする。
- 既存アプリ利用者向け API には影響を与えず、内部運用機能として分離する。
- サンプル用途として、環境差分なし（`dev/stg/prod` すべて同一）で実行可能にする。

## スコープ
- 対象領域: `infra/`（必要に応じて Lambda ソース格納ディレクトリを含む）
- 対象内容:
  - Todo 削除用 Lambda 関数の追加
  - Lambda 実行ロールと必要最小限の DB 接続権限付与
  - 手動実行（AWS マネジメントコンソール）前提の実行入力仕様定義
  - `cdk synth` によるテンプレート合成確認

## 対象外
- 管理者向け Web 画面の追加
- 既存 Todo API への削除専用エンドポイント追加
- 自動スケジュール実行（EventBridge Scheduler など）
- 負荷テストユーザー作成機能自体の実装

## ユーザーストーリー / 利用シナリオ
- 運用者として、負荷テスト終了後に Lambda を手動実行し、不要データをまとめて削除したい。
- 検証担当者として、`userPrefix=loadtest_` でテストデータのみを削除したい。
- 検証担当者として、必要時は `userPrefix=*` を指定し、全ユーザーの Todo を削除したい。

## 機能要件
- FR-01 Lambda バッチ実装
  - Todo クリーンアップ専用の Lambda 関数を追加する。
  - ランタイムは `Python 3.13` を使用する。
  - Lambda は Aurora PostgreSQL に接続し、条件に一致する Todo を削除できること。

- FR-02 起動方法
  - 起動方法は AWS Lambda マネジメントコンソールからの手動実行のみを正式手順とする。
  - CLI、Scheduler、Step Functions などの補助導線は本件では必須としない。

- FR-03 実行権限
  - Lambda 関数をマネジメントコンソールから実行できる IAM 権限を持つ利用者は、実行を許可対象とする。
  - アプリケーション内の管理者ユーザー認証は要求しない。

- FR-04 削除条件
  - 実行入力として `userPrefix` を受け取る。
  - `userPrefix=loadtest_` を指定した場合は、該当プレフィックスのユーザー Todo のみ削除する。
  - `userPrefix=*` を指定した場合は、全ユーザーの Todo を削除対象とする。
  - 上記以外の値は不正入力として失敗扱いにする。

- FR-05 実行対象環境
  - `dev/stg/prod` のすべてで実行可能とする。
  - 本件において `prod` 実行の機能制限は設けない。

- FR-06 実行結果
  - 実行ログに少なくとも以下を出力する:
    - 実行開始/終了時刻
    - 指定された `userPrefix`
    - 削除対象件数と削除完了件数
    - 成功/失敗ステータス

## 非機能要件
- セキュリティ
  - Lambda 実行ロールの権限は、対象 DB と必要なログ出力権限に限定する。
  - シークレット値は Secrets Manager 経由で参照し、コードへハードコードしない。

- 信頼性
  - 大量データ削除時のタイムアウト回避のため、削除処理は分割実行（バッチ削除）を前提に実装する。
  - エラー時に CloudWatch Logs から原因追跡できること。

- 運用性
  - 手動実行手順を `infra/README.md` または `docs/infra/` に記載する更新要否を確認する。

## 受け入れ条件
- AC-01 `infra/` 配下に Todo クリーンアップ用 Lambda（Python 3.13）の定義が追加されている。
- AC-02 Lambda の実行入力で `userPrefix=loadtest_` と `userPrefix=*` の両方を受け付ける。
- AC-03 不正な `userPrefix` 入力時に処理が失敗し、エラーログが出力される。
- AC-04 `prod` を含む各環境向け CDK 合成（`npx cdk synth -c env=<env>`）が成功する。
- AC-05 実行手順が「Lambda マネジメントコンソールから手動起動」であることが仕様として明記されている。
- AC-06 変更範囲が本件に必要な領域に限定されている。

## 制約
- 本件では管理者 UI/API を追加しないため、運用導線は AWS コンソール操作に依存する。
- 全件削除（`userPrefix=*`）は強力な操作であるため、仕様上は許可するが運用時の確認手順は別途定義が必要である。
- サンプルアプリ要件により、`prod` 向け実行抑止は導入しない。

## 依存関係
- `infra/lib/` 配下の既存 ECS/Aurora/Secrets Manager 関連 Construct
- Aurora PostgreSQL の Todo テーブル定義
- AWS Lambda（Python 3.13 ランタイム）
- CloudWatch Logs
